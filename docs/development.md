## Requirements

- **Go 1.27+** (see `go.mod`; the module pins `tinygo.org/x/bluetooth` and
  `github.com/hybridgroup/go-bthome`)
- **macOS**: Xcode command line tools (`xcode-select --install`) — CoreBluetooth
  is used through cgo, so the binary must be built *on* macOS (no cross
  compiling). The first run triggers the Bluetooth permission prompt for the
  terminal app.
- **Linux**: BlueZ (≥ 5.48 recommended) — the tinygo bluetooth package talks to
  it over D-Bus. Root is not required if the user is in the `bluetooth` group.
- **Venus OS GX device** (only for end-to-end tests against Victron): Venus OS
  with the `dbus-ble-sensors` UDP gateway socket (firmware with
  `/Settings/BleSensors/Socket/*`), *Bluetooth sensors* enabled.

## Building

```
go build -o thermobeacon-ble-go .
```

For the GX device (or any Linux host), build on Linux:

```
GOOS=linux GOARCH=arm64 go build -o thermobeacon-ble-go-linux-arm64 .
```

Cross compiling **to** macOS does not work (cgo); build on the Mac itself and
copy the binary if needed.

Inject the version shown by `thermobeacon-ble-go -version` and in the startup
log:

```
go build -trimpath -ldflags "-s -w -X main.version=v0.1.0" -o thermobeacon-ble-go .
```

### Releases

The release workflow (`.github/workflows/release.yml`) runs on every `v*` tag:

1. runs the test suite on Ubuntu and macOS,
2. builds `linux-amd64`, `linux-arm64` and `linux-armv7` with
   `CGO_ENABLED=0` (statically linked — ideal for Venus OS: no libc
   dependency; `armv7` is what a Cerbo GX runs, `arm64` an Ekrano GX),
3. builds `darwin-arm64` and `darwin-amd64` on a macOS runner with
   `CGO_ENABLED=1` (CoreBluetooth needs cgo; the amd64 binary is cross
   compiled from the arm64 runner with Apple clang),
4. creates a GitHub release from the tag with generated release notes,
   `*.tar.gz` (linux) / `*.zip` (macOS) assets and a `SHA256SUMS.txt`.

To cut a release:

```
git tag v0.1.0
git push origin v0.1.0
```

## Running the tests

```
go test ./...          # all tests
go test -count=1 -v ./...
go vet ./...
gofmt -l .
```

The test suite needs no Bluetooth hardware. It covers, among others:

- ThermoBeacon decoding: reference payload, negative temperatures, button
  flag, MAC validation (LSB/MSB first), macOS company-id path, min/max packet
  rejection
- Govee decoding: H5074, H5072/H5075 packed values (incl. negative), H51xx
  family, error bit, out-of-range rejection, name/company-id matching
- BTHome decoding: TLV parsing, the humidity factor correction, malformed and
  unsupported payloads
- Ruuvi RAWv2 encoding and the UDP packet: **expected bytes generated by
  running the original Python implementation** of `dbus-ble-temp`, so the
  wire format is verified to be byte-for-byte identical
- Bridge behaviour: rate limiting, `-no-forward`, sender failures, sequence
  number choice, once-per-device foreign logging, state file roundtrip
- Dump output: annotated breakdowns for all three formats

## Project layout

| File | Purpose |
|---|---|
| `main.go` | flags, subcommands (`list`, `dump`), scan lifecycle, signal handling |
| `config.go` | runtime options, device filter, `debugf` |
| `sensor.go` | `Reading` type, MAC helpers, pseudo MAC, voltage derivation |
| `thermobeacon.go` | ThermoBeacon decoder (port of the original Python decoder) |
| `govee.go` | Govee decoder (H5074, H5072/H5075, H51xx family) |
| `bthome.go` | BTHome v2 decoder via go-bthome, payload pre-validation |
| `ruuvi.go` | RuuviTag RAWv2 encoder + dbus-ble-sensors UDP packet v1 |
| `bridge.go` | scan callback, decoders wiring, rate limiting, forwarding, idle watchdog, UDP sender |
| `dump.go` | annotated payload dumps for `-debug` / `dump` |
| `state.go` | `sensors.json` seen store and the `list` output |

Dependency notes:

- `tinygo.org/x/bluetooth` is pinned to the version `go-bthome` was built
  against (`v0.10.1-0.2025...`). Its `AdvertisementPayload` exposes
  manufacturer/service data as parsed elements (`CompanyID` + `Data`); on
  macOS `Bytes()` returns nil, so the dump works from the structured fields.
- `go-bthome` is minimal: `Payload.Parse` panics on unknown type ids and
  truncated values, `GetDataValue` returns nil for uint/string types, and its
  humidity factor for type `0x03` contradicts the BTHome spec. `bthome.go`
  works around all three; keep that in mind when upgrading it.

## Data flow in code

```
adapter.Scan                     (main.go)
  └─ Bridge.HandleScan           (bridge.go)
       ├─ acceptsDevice          (config.go)        device filter, -device
       ├─ debugDumpScan          (dump.go)          annotated hex + field dump
       ├─ decodeThermoBeacon     (thermobeacon.go)  18-byte manufacturer data
       ├─ decodeGovee            (govee.go)         0xEC88 / 0x0001 layouts
       ├─ decodeBTHome           (bthome.go)        service data 0xFCD2
       └─ Bridge.forward         (bridge.go)
            ├─ rate limit per MAC (min-interval)
            ├─ encodeRuuviRAWv2   (ruuvi.go)         24-byte payload
            ├─ buildUDPPacket     (ruuvi.go)         gateway packet v1
            ├─ udpSender.send     (bridge.go)        WriteTo 127.0.0.1:18542
            ├─ debugDumpRuuvi     (dump.go)          RAWv2 field dump
            └─ SeenStore.Update   (state.go)         sensors.json
```

The `Reading` struct (`sensor.go`) is the boundary between decoding and
forwarding: decoders fill it, the bridge only forwards it. Add new fields
there (and to `SensorEntry` in `state.go`) if a new format carries more data.

## Adding a new sensor format

1. **Decoder** — new file `yourformat.go` with
   `decodeYourFormat(mac string, companyID uint16, data []byte) (*Reading, error)`.
   Validate strictly (length, magic bytes, value ranges) and return a
   descriptive error — the dump shows rejection reasons to users.
2. **Wire it** — call it in `Bridge.HandleScan` at the right place in the
   manufacturer-data / service-data chain, and in `dumpScanResultText`
   (`dump.go`) so `-debug` shows the field breakdown.
3. **Dump** — add a `writeYourFormatFields` breakdown in `dump.go` following
   the existing table style (`goveeRow`).
4. **Identity** — if the payload does not carry a MAC, let the bridge assign
   `identityFor(senderMAC, addr)` (advertiser MAC or pseudo MAC on macOS).
5. **Model** — set `Reading.Model` when the exact model is known; it shows up
   in logs (`Govee H5074 ...`) and in `sensors.json`.
6. **Tests** — decoder tests with real captured payloads (include a negative
   temperature and a rejection case), a dump test, and if the format needs new
   RAWv2 mappings, verify against the reference implementation.

## Debugging tools

- `./thermobeacon-ble-go dump` — scan everything, decode and dump each
  advertisement without forwarding. Use this to find device UUIDs/MACs and to
  inspect unknown payloads.
- `./thermobeacon-ble-go -debug` — follow the configured device with dumps of
  every advertisement and every forwarded packet.
- Watch what would arrive at Victron's socket, without a GX:

  ```
  nc -klu 127.0.0.1 18542 | xxd -
  ```

  With `-udp-host 127.0.0.1 -udp-port 18542`, every 36-byte packet (24-byte
  RAWv2 payload at offset 11) can be inspected live.
- `./thermobeacon-ble-go list` — the seen-sensor table from `sensors.json`.
- On the GX: `dbus -y com.victronenergy.settings
  /Settings/BleSensors/Socket/BindAddress GetValue` must return
  `127.0.0.1` (or the address you send to), and the service must be running:

  ```
  svstat /service/dbus-ble-sensors
  tail -F /var/log/dbus-ble-sensors/current | tai64nlocal
  ```
